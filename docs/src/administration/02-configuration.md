# Configuring Threadlight

Threadlight comes with sensible defaults that let you start the server with almost no setup at all. But as your community grows, you will want to tell Threadlight a few things about itself so it behaves the way you need it to. You do this by setting a handful of configuration values, most of which are passed to the server through a file called a dotenv file or through environment variables on your system.

The most important setting is the JWT secret. Think of this as the master key that the server uses to keep your community members logged in securely. When someone logs into Threadlight, the server creates a special digital token that proves who they are. The JWT secret is the ingredient that makes those tokens impossible to fake. You should set this to a long, random string that only you know. If someone else gets hold of this secret, they could forge login tokens and impersonate any member of your community. So treat it like the key to your front door.

Next, the server needs to know how to reach your database. This is your PostgreSQL connection string, which tells Threadlight where the database lives, what its name is, and which user account to use when accessing it. The connection string contains the address of the database server, usually something like localhost if both are on the same machine, along with the database name, your username, and your password. This is the only way Threadlight talks to its filing cabinet, so make sure this information is correct. If the database is on a different computer, you will need to provide its network address and make sure that computer allows connections from your Threadlight server.

Redis needs its own connection information too. Redis is the fast memory helper that Threadlight uses for things that need to happen quickly, like checking affinity scores between users or keeping temporary data around. The Redis connection string is simpler than the database one — just an address and a port number. If Redis is on the same machine, the address will be localhost with the default port. Threadlight will create and clean up its own data inside Redis, so you do not need to prepare anything on the Redis side ahead of time.

You can also tell Threadlight which network port to listen on and which network address to bind to. The port is like a door that people knock on when they visit your server from their web browser. The default port is usually fine for testing, but if you already have another web service running on that same port, you can change Threadlight to use a different one. The host or bind address tells the server which network connections to accept. If you set it to localhost, only programs on the same machine can reach Threadlight. If you set it to zero point zero point zero point zero, the server will accept connections from anywhere on your network, which is what you want when you open it up for the whole internet.

Log level controls how much detail the server writes to its log. During the early days when you are learning how Threadlight behaves, you might want more detail so you can see exactly what the server is doing at every moment. Once everything is running smoothly, you can turn the log level down to reduce the amount of text flowing by. The logs themselves are printed to the standard output, which means you can view them in your terminal or capture them with whatever logging tool your system uses.

Content pruning settings let you decide how aggressively the server cleans up old or ignored posts. By default, Threadlight removes posts that are older than six months and have very few likes, because those posts are unlikely to be useful to anyone anymore. You can change the age threshold and the minimum number of likes required for a post to be kept around. This is entirely up to you and depends on how much storage you have and how important it is to keep every piece of content ever created. If your community is small and your disk space is plentiful, you might keep posts around longer. If you are running on a tiny computer with limited storage, you might prune more aggressively.

All of these configuration values can be set in a file that sits next to your Threadlight binary. The server reads this file when it starts up, so any time you change a setting, you need to restart the server for the new value to take effect. If you are running Threadlight as a system service, this usually means a simple restart command. The server is designed to be up front about what it is doing, so when you start it with your configuration, it will print a summary of the settings it loaded, letting you verify that everything looks right before your community starts using it.
