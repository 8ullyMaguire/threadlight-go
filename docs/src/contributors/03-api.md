# API Philosophy

Threadlight's API is the bridge between the frontend you see in your browser and the server that does all the behind-the-scenes work. It is designed to be simple, predictable, and easy to understand, because the goal is not to impress you with clever tricks but to let you build things that work. Whether you are writing a new feature for the frontend, building a bot that interacts with Threadlight, or creating your own client application, the API follows a set of patterns that will feel familiar after a short while.

The API is RESTful, which is a fancy way of saying that it treats everything as a resource with a clear address. Users are a resource, posts are a resource, communities are a resource. Each resource has its own address, and you interact with it using standard methods that mean the same thing everywhere. To read a list of posts, you send a GET request to the posts address. To create a new post, you send a POST request to the same address with the post content in the body. To update something, you send a PUT or PATCH request. To delete something, you send a DELETE request. Every action follows this same pattern, so once you understand how one resource works, you understand how all of them work.

All data sent to and from the API is in JSON, a simple text format that both humans and computers can read easily. When you send a request with data in it, you set the content type header to tell the server you are sending JSON. When the server responds, it sends JSON back, with the data you asked for and some extra information about whether the request succeeded or ran into a problem. If something goes wrong, the response includes a clear error message and a status code that tells you what kind of problem it was — a code in the four hundreds means you sent something the server did not like, and a code in the five hundreds means something broke on the server side.

Most requests that change data or read private information require authentication, which is the way the server knows who you are. When you log in through the frontend, the server gives you a token — a long string of characters that proves you are who you say you are. You send this token along with every request that needs it, using a header named Authorization. The token expires after a while for safety, and you can get a new one by logging in again or using a refresh token if the API provides one. Public data, like the list of communities or a public post, can be read without a token, but anything that touches your account needs one.

The API is versioned, which means the addresses all start with a version number like v1. This is a promise from the developers that once something works with version one of the API, it will keep working even if a newer version comes out. When changes are big enough that old code might break, a new version is created, and the old one sticks around so nothing stops working unexpectedly. You can always tell which version you are using by looking at the address, and you can choose to upgrade to a newer version when you are ready.

To discover all the endpoints the API offers, the best place to start is the server code itself. The router file in the internal api folder lists every available address and what it does. Each handler file shows you exactly what data it expects and what it returns. Reading the router file from top to bottom gives you a map of the entire API. Another good approach is to watch what the frontend does while you use Threadlight — open your browser's developer tools, look at the network tab, and you will see every request the frontend makes, including the addresses, the data it sends, and the responses it gets back. This is often the fastest way to learn how things work in practice.

The API is meant to be a tool, not a puzzle. It follows consistent rules, returns clear errors, and stays out of your way so you can focus on building whatever you are building. If something is confusing or does not behave the way you expect, that is a bug worth reporting.
